# Desktop 작업 지침

## 1. 목표와 기준 구현

- Android 앱을 기능, 상태 전이, 문구 및 시각 디자인의 기준 구현으로 삼는다.
- Desktop은 Android와 동일한 사용자 목적과 기능을 제공하되 Screen은 별도로 구현한다.
- Desktop이라는 이유로 UI 디자인이나 정보 구조를 임의로 바꾸지 않는다.
- 창 크기, 스크롤, 포커스, 키보드 및 마우스 입력처럼 플랫폼상 필요한 차이만 적용한다.
- Android 기능이나 화면이 변경되면 대응하는 Desktop 구현에 미치는 영향도 검토한다.
- Desktop 구현을 쉽게 만들기 위한 목적으로 Android 동작이나 화면을 변경하지 않는다.

## 2. 지원 플랫폼: Windows 전용

- `desktopApp`의 제품 지원 대상은 Windows뿐이다.
- macOS와 Linux용 앱, 설치 패키지, 플랫폼 기능 및 호환성은 구현하거나 검증할 필요가 없다.
- JVM 또는 Compose Desktop이 여러 운영체제에서 실행된다는 이유로 크로스 플랫폼 호환성을 요구사항에 추가하지 않는다.
- 플랫폼별 구현과 라이브러리를 선택할 때 Windows에서의 안정성, 공식 지원, 배포 및 사용자 경험을 우선한다.
- macOS나 Linux를 지원하기 위해 Windows 구현을 우회하거나 기능을 축소하지 않는다.
- 개발 장비에서의 임시 실행 여부는 Windows 지원을 대신하는 완료 기준이 아니다. Windows 전용 기능과 최종 동작은 Windows 환경에서 검증한다.
- 배포 산출물은 Windows용 MSI 또는 EXE를 기준으로 구성한다.

## 3. 트레이 기반 애플리케이션 수명주기

- `desktopApp`은 실행되는 동안 Windows 시스템 트레이에 상주하는 프로그램으로 구현한다.
- 동일한 Windows 사용자 세션에서는 `desktopApp` 프로세스를 하나만 실행한다.
- 프로그램을 다시 실행하면 새 창과 트레이 아이콘을 만들지 않고, 이미 실행 중인 창을 정상 상태로 복원해 전면에 표시한다.
- 단일 인스턴스 잠금은 Compose 창, 트레이 아이콘 및 애플리케이션 범위 리소스를 만들기 전에 획득하고, 트레이 메뉴의 `종료`로 실제 종료할 때 해제한다.
- 트레이 아이콘은 자동 로그인이나 알림 설정 여부와 관계없이 프로그램 시작 시 생성하고 실제 종료 시까지 유지한다.
- 창의 닫기 버튼과 `Alt+F4`는 프로세스를 종료하지 않고 창을 트레이로 숨긴다.
- 창 최소화 버튼은 Windows 기본 동작을 유지하며 작업 표시줄에 최소화된 창을 남긴다.
- 숨겨진 창은 트레이 아이콘을 더블 클릭하거나 트레이 메뉴의 `SSUTime 열기`를 선택했을 때 정상 상태로 복원하고 전면에 표시한다.
- 정상적인 완전 종료 진입점은 트레이 아이콘을 우클릭해 표시되는 메뉴의 `종료`뿐이다.
- 알림 설정을 끄면 마감 알림만 중단하며 트레이 아이콘이나 애플리케이션 수명주기는 종료하지 않는다.
- 로그아웃, 로그인 실패, 창 숨김 및 최소화는 프로세스를 종료하지 않는다.
- 마감 알림 스케줄러는 창의 표시 여부와 분리한다. 알림을 켠 상태라면 창이 트레이에 숨겨져 있어도 지정된 시간에 계속 확인하고 알림을 표시한다.
- HTTP 클라이언트, 트레이 아이콘 및 기타 애플리케이션 범위 리소스는 트레이 메뉴의 `종료`로 실제 애플리케이션이 종료될 때 정리한다.
- 시스템 트레이를 만들 수 없는 예외 환경에서는 창 닫기나 최소화로 복구할 수 없는 백그라운드 프로세스를 만들지 않는다.

## 4. 필수 작업 하네스

Desktop 기능을 추가하거나 변경할 때마다 다음 순서를 지킨다.

1. 대응하는 Android Screen, ViewModel, Navigation, Repository 및 리소스를 확인한다.
2. Android 기능을 사용자 동작과 상태 전이 단위로 목록화한다.
3. 각 기능의 Windows 및 Compose Desktop JVM 지원 여부를 최신 공식 문서와 라이브러리 자료로 확인한다.
4. 아래 지원 여부 판정표에 따라 직접 구현, Desktop 대체 구현 또는 제외로 분류한다.
5. 지원되는 기능과 대체 가능한 기능을 구현하고, 지원 불가능한 기능만 건너뛴다.
6. 정상, 로딩, 빈 상태, 오류, 재시도 및 세션 만료 흐름을 검증한다.
7. 구현 결과와 제외 또는 대체한 기능을 사용자에게 보고한다.

일부 기능이 지원되지 않는다는 이유로 나머지 구현 가능한 기능까지 중단하지 않는다. 다만 제외로 인해 핵심 사용자 목적을 달성할 수 없거나 제품 동작이 크게 달라지는 경우에는 임의로 결정하지 않고 사용자에게 알린다.

## 5. Windows 구현 가능성 판정

플랫폼 기능은 기억이나 추측에 의존하지 않고 작업 시점의 최신 공식 자료로 확인한다. 단순히 의존성이 컴파일된다는 사실만으로 실제 수신, 백그라운드 실행, 패키징 및 배포 환경에서 정상 동작한다고 판단하지 않는다.

| 판정 | 기준 | 처리 |
| --- | --- | --- |
| 직접 지원 | Compose Desktop JVM 또는 Windows에서 공식적으로 지원된다. | 공식 방식으로 구현한다. |
| 대체 가능 | Android API는 사용할 수 없지만 동일한 사용자 목적을 달성하는 Windows 방식이 있다. | 요구사항, 패키징 및 운영 영향을 확인한 뒤 Desktop 방식으로 구현한다. |
| 지원 불가 | 공식 지원과 합리적인 Desktop 대체 수단이 모두 없다. | 해당 기능만 건너뛰고 이유와 영향을 사용자에게 보고한다. |

- 지원 여부를 확인할 때 JVM 호환성뿐 아니라 Windows 버전, 백그라운드 동작, 패키지 형식, 권한, 계정 등록, 배포 방식 및 운영 비용도 확인한다.
- 비공식 우회 구현이나 지원되지 않는 SDK 사용을 기본 해법으로 선택하지 않는다. 필요한 경우 위험과 유지보수 영향을 먼저 설명하고 사용자 동의를 받는다.
- 서버용 Admin SDK를 Desktop 클라이언트 SDK의 대체품으로 사용하지 않는다.

## 6. Android 전용 기능과 예외 처리

- 전화 상태에 연동하는 알림처럼 Android 또는 모바일 환경에서만 의미 있게 구현할 수 있고 합리적인 Desktop 대체 수단이 없는 기능은 Desktop 동등성 대상에서 제외한다.
- Android 전용 기능이라도 사용자 목적을 충족하는 합리적인 Windows 대체 수단이 있으면 Desktop 방식으로 구현한다.
- FCM 클라이언트처럼 Compose Desktop JVM에서 공식 지원되지 않는 기능은 직접 이식하지 않는다. 예를 들어 Desktop 로그인은 FCM 토큰 등록 단계를 건너뛰고도 로그인과 다음 화면 이동을 정상적으로 완료해야 한다.
- 알림 기능 자체가 필요하다면 FCM 사용 여부와 별개로 Windows 알림, WNS, WebSocket, SSE 또는 폴링 등 가능한 Desktop 방식을 당시 공식 지원 범위에 따라 다시 조사한다.
- Android 전용 후처리가 지원되지 않거나 실패하더라도 핵심 기능의 성공 처리와 다음 화면 이동을 막지 않는다.
- 제외한 기능 때문에 빈 영역, 사용할 수 없는 버튼, 끊긴 탐색 경로 또는 불필요한 권한 안내를 남기지 않는다.
- 제외한 단계나 UI는 숨기거나 건너뛰고 주변 요소를 자연스럽게 재배치한다.
- 제외하거나 대체한 기능은 대응하는 Android 기능, 판단 근거, 사용자 영향 및 Desktop 처리 방식을 코드 또는 작업 기록에 명시한다.

## 7. 코드와 모듈 경계

- Android와 Desktop의 Screen 구현을 공유하지 않는다.
- `commonMain`에는 전체 화면, `Scaffold`, 창 관리 또는 플랫폼 제스처를 두지 않는다.
- 디자인 토큰과 비즈니스 상태/API만 공통화한다.
- 공통 컴포넌트는 양쪽 동작, 레이아웃 및 클릭 영역이 검증된 경우에만 사용한다.
- Desktop에서 Android `app` 모듈을 직접 의존하지 않는다.
- Desktop 코드에서 `android.*`, `Context`, `Intent` 또는 Android `R` 리소스를 참조하지 않는다.
- Android 전용 기능은 공통 코드에 끌어들이지 않고 플랫폼 인터페이스 뒤에 둔다.

## 8. 기능 동등성 기준

- 입력 검증, 로딩, 성공, 빈 상태, 오류, 재시도, 세션 만료, 자동 로그인 및 화면 이동을 Android와 동일한 상태 전이로 제공한다.
- 실제 API와 상태 처리가 연결되지 않은 임시 성공 화면, 하드코딩 데이터 및 가짜 완료 메시지를 기능 구현으로 간주하지 않는다.
- 플랫폼 예외로 명시된 기능을 제외하면 Android에서 가능한 주요 상호작용을 Desktop에서도 완료할 수 있어야 한다.
- 클릭 영역, 포커스 이동, 키보드 입력 및 창 크기 변화에서 Desktop 사용성을 별도로 확인한다.

## 9. 완료 검증 체크리스트

- [ ] 대응하는 Android 구현과 사용자 흐름을 확인했다.
- [ ] 추가한 모든 플랫폼 기능의 최신 Windows 지원 여부를 공식 자료로 확인했다.
- [ ] 직접 지원, 대체 가능 및 지원 불가 기능을 구분했다.
- [ ] 실제 API와 상태 로직이 연결되어 있다.
- [ ] 정상, 로딩, 빈 상태, 오류, 재시도 및 세션 만료를 확인했다.
- [ ] 제외 기능으로 인한 빈 UI나 끊긴 흐름이 없다.
- [ ] Windows 환경에서 Windows 전용 기능과 실제 사용자 흐름을 확인했다.
- [ ] 닫기와 `Alt+F4`가 프로세스를 종료하지 않고 트레이로 숨기는지 확인했다.
- [ ] 최소화 버튼이 Windows 기본 동작대로 창을 작업 표시줄에 최소화하는지 확인했다.
- [ ] 트레이에서 창 열기와 우클릭 메뉴의 `종료`가 각각 복원과 완전 종료로 동작하는지 확인했다.
- [ ] 실행 파일을 여러 번 실행해도 프로세스와 트레이 아이콘이 하나만 유지되고 기존 창이 복원되는지 확인했다.
- [ ] 창이 트레이에 숨겨진 상태에서도 설정된 마감 알림이 동작하는지 확인했다.
- [ ] macOS 또는 Linux 호환성을 위해 Windows 구현을 변경하거나 축소하지 않았다.
- [ ] Android와 Desktop의 관련 빌드 및 테스트를 실행했다.
- [ ] 제외하거나 대체한 기능과 검증 결과를 사용자에게 보고했다.

## 10. 작업 결과 보고 형식

Desktop 작업 완료 시 다음 항목을 구분해서 알린다.

- 구현 완료: Android와 동일하게 제공한 기능
- Desktop 대체: Windows 방식으로 변경해 제공한 기능과 변경 이유
- 제외: 구현할 수 없는 기능, 공식 근거, 사용자 영향 및 건너뛴 방식
- 검증: 실행한 빌드, 테스트 및 수동 확인 결과
